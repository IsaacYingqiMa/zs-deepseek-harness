# zs-dev-orchestrator 9 stage 详细定义

> Layer 2 stage 编排 Agent 派 CC 时,本文件是"目标定义"的唯一来源。
> Layer 2 不重新定义 stage 做什么——只在本文件基础上加项目特定补充。

---

## 1. brain(需求讨论 / 范围收敛)

**通用目标**:把模糊需求收敛为可进入下一阶段的结构化讨论结论。

**必跑条件**:
- 任务类型 T1(新建) / T3(重构) / T6(翻译/移植)
- 任务类型 T2(变更/Bug):仅在 change 判"重大变更"或边界变化时跑

**输入**:
- 用户原始需求
- 项目画像
- 现有业务对象目录(避免重复造轮子)

**输出**(8 项结构化结论):
1. 目标 / 背景
2. 核心问题
3. 推荐方案(2-3 个 + 推荐 + 不推荐原因)
4. 范围内内容
5. 明确不做的内容
6. 成功标准
7. 待确认事项
8. 建议模块名(命名遵循项目 spec_system.naming_convention)

**验收标准**:
- 8 项齐备
- 不存在关键双义性或未取舍方案
- 模块名与现有命名一致(查 spec_system 历史)
- 推荐方案给出明确推荐 + 理由

**禁止行为**:
- 不写代码
- 不写 spec 文档
- 不写 TASK 任务表
- 不假设任何架构

---

## 2. spec(spec 文档生成 / 更新)

**通用目标**:基于已收敛结论生成/更新模块级 spec 文档。

**必跑条件**:
- 任务类型 T1 / T3 / T6
- change 判"spec 补充"或"小范围变更"时(增量更新)

**输入**:
- brain 结论
- 项目 spec_system 定义(zsspec / markdown / custom / none)
- spec 模板(如有)

**输出**(根据 spec_system.type 不同而不同):

| spec_system.type | 必产物 |
|---|---|
| zsspec | REQ-{模块}.md + DES-{模块}-前端.md + DES-{模块}-后端.md + TASK-{模块}.md |
| markdown | docs/spec/{模块}/spec.md + design.md + tasks.md |
| custom | 按项目 README 或 spec_system.template_path 推断 |
| none | 由 spec_system.spec_root 默认推断,或建 docs/{模块}/ 目录 |

**验收标准**:
- 必产物文件全部存在
- 命名符合 naming_convention
- 编号/版本/路径/引用一致
- 不存在关键断链或关键遗漏
- 关键歧义已收敛(否则报 needs_user)

**禁止行为**:
- 不写代码
- 不进入 apply
- 不在 spec 完成后自动进 apply(必须经 verify)

---

## 3. test-gen(验收清单生成)

**通用目标**:基于 spec 生成验收清单(测试用例)。

**必跑条件**:
- 任务类型 T1 必跑
- T3 / T6 可选(由 Layer 2 决定)

**输入**:
- spec 文档全文
- 项目 test_system 定义

**输出**:
- 验收清单(zsspec 走 CHK,其他走 spec_system 推断)

**每条验收项必含**:
- 编号(遵循项目命名)
- 关联需求
- 检查目的
- 检查步骤
- 预期结果
- 证据要求
- 等级(阻塞 / 重要 / 建议)
- automation 标记(static / auto / manual)
- 状态(待执行 / 通过 / 失败 / 阻塞 / 跳过 / 废弃)

**验收标准**:
- 必产物文件存在
- 命名规范
- static / auto / manual 分类合法
- 每条有证据要求
- 无主功能缺失(对照 REQ 逐条核对)

---

## 4. verify(spec 一致性校验 + 门禁)

**通用目标**:在进入 apply 前,对当前 spec 做一致性校验,决定是否可开工。

**必跑条件**:
- spec 后必经
- apply 之前必经

**输入**:
- spec 文档全文
- 项目 hard_constraints_doc
- 现有业务对象

**校验维度**(10 项,跨项目通用):

1. 编号追溯 — 任务/验收项引用的需求存在
2. 需求覆盖 — 关键验收标准都有对应检查项
3. 设计一致 — API 契约 / 数据结构 / 状态流与需求匹配
4. 任务完整 — 任务覆盖了全部关键功能点
5. 版本一致 — 文档版本号同步
6. 文档齐套 — 必产物完整
7. 模块覆盖地图 — 需求/设计/任务/验收的模块集合一致
8. 跨模块依赖 — 依赖模块存在且合理
9. 全局 NFR / 模块验证覆盖 — NFR 有对应检查项
10. 命名与路径规范 — 文件名 / 目录层级 / 编号格式合规

**结论分级**:
- 可开工 — 全部通过
- 有条件可开工 — 存在少量非阻断问题
- 暂不可开工 — 存在阻断问题

**输出**:verify 报告
```
## 一致性检查报告
- 结论: <可开工|有条件可开工|暂不可开工>
- 通过项: <N>
- 失败项: <N>
- 警告项: <N>
- 必须确认: <列表,空表示无>
- 详细列表: <逐条列出>
```

**Hermes 行为**:
- 可开工 → 推 stage 完成,进 apply
- 有条件可开工 → 派 CC 修订警告项,重 verify
- 暂不可开工 → 派 CC 修订 spec,重 verify(3 次后升级用户)

## 5. change(变更分类 + 路由)

**通用目标**:把变更分类,决定走哪个处理方式。

**必跑条件**:
- 任务类型 T2(变更/Bug 修复)必经

**输入**:
- 变更描述
- 现有 spec 文档
- 现有代码

**变更分类**:
| 类型 | 判断标准 | 处理方式 |
|---|---|---|
| 文档纠错 | 不改变功能/范围/设计 | 直接修正文档 |
| spec 补充 | 属于原边界内的遗漏 | 修订 spec,版本号 +1 |
| 小范围变更 | 局部设计调整,仍在模块边界内 | 修订 spec,重开 task |
| 重大变更 | 原理解有误 / 方案需重选 / 边界要调整 | 回退到 brain |
| Bug 修复 | 实现与 spec 不符 | 小:直接修;大:回退到 spec |

**输出**:变更处理报告(变更类型 + 影响范围 + 处理方式 + 已修正内容)

---

## 6. apply(实施代码 / 文档)

**通用目标**:基于已 verify 过的 spec 实施代码/文档。

**必跑条件**:
- 所有任务必跑(T2 是 [apply],但仍是必经 stage 之一)

**输入**:
- verify 报告
- spec 文档
- 项目业务对象目录(放产物到正确位置)
- 项目 hard_constraints_doc

**输出**:
- 代码文件(路径见 business_objects.*_dir)
- utils 函数(路径见项目约定)
- 路由/接口(路径见 business_objects.routes_dir)
- 单元测试(路径见 test_system.test_root)
- TASK 状态回写(每个 task 完成后立即)
- CHK 状态回写(apply 不回写 CHK,留给 code-review / e2e-run)

**强制行为**:
- 每个 task 完成后立即回写 TASK 状态为"已完成"
- 实施范围严格不超 task,超出立即停
- 收口前核对 TASK 状态与代码进度一致
- 至少 1 次基础测试(单元测试 / 接口测试)

**验收标准**:
- 必产物文件全部存在
- 导入路径正确(如 agno_agent.* / 其他项目约定)
- 至少 1 个测试通过
- TASK 状态与代码一致
- 不存在未回写的 task

**禁止行为**:
- 不修改不归本模块的文件
- 不引入新依赖不说明
- 不把"未完成"标"已完成"
- 不写死配置
- 不跳过测试
- 不修改 .meta-dev/ 任何文件

---

## 7. code-review(静态审查)

**通用目标**:基于 static 检查项做结构化静态代码审查。

**必跑条件**:
- 任务类型 T1 / T3 必跑
- T2 视情况(看变更范围)

**输入**:
- test-gen 产物的 static 检查项
- git diff(本轮 apply 改了什么)
- 现有代码风格

**审查维度**(由 test-gen 决定,但默认覆盖):
- 命名规范
- 类型一致性
- 错误处理
- 安全漏洞
- 性能反模式
- spec 一致性(代码实现是否真的做了 spec 要求)
- 跨模块边界
- 公共组件回归

**输出**:code-review 报告
```
## 静态审查报告
- 维度: <N>
- 通过: <N>
- 失败: <N>(每条带文件:行号 + 修复建议)
- 警告: <N>
- 严重问题: <列表>
```

**Hermes 行为**:
- 全部通过 → 推 stage 完成
- 存在失败 → 派 CC 修复后重审
- 存在严重问题 → 升级用户

---

## 8. e2e-gen(端到端测试代码生成)

**通用目标**:基于 auto 检查项生成端到端测试代码。

**必跑条件**:
- 任务类型 T1 必跑
- T3 / T6 可选(由 Layer 2 决定)

**输入**:
- test-gen 产物的 auto 检查项
- 项目 e2e_runner(如 playwright / cypress)

**输出**:
- e2e 测试代码(路径见 test_system.test_root/e2e/ 或项目约定)
- 不执行测试,只生成

**验收标准**:
- 测试代码可独立运行
- 每个 auto 项对应一个测试用例
- 不执行测试

---

## 9. e2e-run(端到端测试执行)

**通用目标**:执行 e2e 测试,回写状态,生成报告。

**必跑条件**:
- e2e-gen 跑过之后
- 任务类型 T1 必跑
- T3 / T6 可选

**输入**:
- e2e-gen 产物的测试代码
- 项目 e2e_runner

**输出**:
- 测试结果(通过/失败/跳过/超时)
- 报告 `.meta-dev/e2e-reports/<时间戳>.md`
- 失败测试附错误截图/日志
- 回写 auto 状态

**Hermes 行为**:
- 全部通过 → 推 stage 完成
- 部分失败 → 派 CC 修复后重跑
- 连续 3 次失败 → 升级用户

---

## 10. done(验收 + 状态收口)

**通用目标**:核对所有状态,做最终验收。

**必跑条件**:
- 所有任务必跑(最后一个 stage)

**输入**:
- 所有 stage 的产物
- spec 文档状态
- test-gen 产物的检查项状态

**验收标准**(必须全部满足):
- 所有 task 状态为"已完成"
- 所有 static 状态为"通过"
- 所有 auto 状态为"通过"
- 所有 manual 状态为"通过"或"跳过"
- 证据齐全
- 无 blocker
- 满足 hard_constraints_doc

**输出**:
- 更新 spec 状态为"已完成"
- 推用户"请最终验收"

**Hermes 行为**:
- 全部满足 → 推飞书"模块 X 完成,请人工验收"(降级到 .meta-dev/notifications.log)
- 任一不满足 → 拒绝更新,按责任阶段打回,派 CC 修复

---

## 跨 stage 通用规则

1. **每个 stage 完成时**:Hermes 写 state.yaml(更新模块的 current_stage 和 stages 列表)
2. **每个 stage 失败时**:Hermes 决策 rewind 或升级
3. **跨 stage 数据流**:每个 stage 的输出 = 下一 stage 的输入,通过 state.yaml 的 stages[].last_output 传递
4. **不重跑 Layer 1**:执行中需要重路由(verify 不过要回 spec),由 Layer 2 决定,Layer 1 只在任务开始时跑 1 次
