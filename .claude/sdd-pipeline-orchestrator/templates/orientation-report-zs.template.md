# Phase 0 产出地图模板

用户原话模式:"先帮我理解我的代码 / 给我梳理一下当前实现 / 我后面有个新需求,你先完整理解"

**重要**:这份模板给 Hermes 自己用,不直接给用户看。用户拿到的是按这份模板填出来的纯文本报告(无需 markdown 标题,但保留代码块)。

---

## 报告骨架(按顺序)

### 段 1:整体定位(3-5 行)

```
{项目名} - {一句话定义}
技术栈: 后端 X + Y / 前端 A + B / 数据层 C / 外部依赖 D
入口路径: HTTP / WS / RPC 入口
协议形式: WS / HTTP / 协议名(一句话说明)
关键角色 / 模型: {1-2 句}
```

### 段 2:协议契约(代码块,字段表)

```
消息 schema(JSON 字段):
- flag ∈ {...}              # 消息大类
- type ∈ {...}              # 消息子类
- result_type ∈ {...}       # 生命周期阶段
- 业务字段: {列关键字段}

端点清单:
- WS /ws/xxx  → 用途 X(鉴权方式)
- HTTP POST /api/yyy  → 用途 Y(参数、返回)

状态码 / 错误码: {列关键几个}
```

### 段 3:主链路(数据流文字描述)

```
入口层: 文件路径 → 关键函数 → 一句话职责
  ↓
协议层: 入口函数调到哪里 → 校验 → 路由
  ↓
编排层: 主流程函数 → 子流程节点(列关键节点名 + 一句话)
  ↓
服务层: 哪些服务并行起 → 各自做什么
  ↓
输出层: 流式/分页/同步返回 → 前端如何消费
```

### 段 4:关键模块清单

```
核心文件(列出 5-10 个最重要的):
- 路径 A → 职责一句话
- 路径 B → 职责一句话
- ...

关键 Redis key:
- key 模式 → 含义 / TTL / 谁读写

关键 DB table:
- table → 用途

外部 API 依赖:
- API 名 → URL → 谁调用

用户最可能想改的扩展点(基于代码现状推测):
- {层名 / 模块名} → 为什么这是扩展点(spec 提了/代码有 TODO/版本历史里有讨论)
```

### 段 5:踩坑信号 / 版本说明(可选,5-10 行)

```
- 哪些 spec 章节已读过但代码未实现
- 哪些代码模块是新加的(spec 可能还没同步)
- 哪些地方 spec 与代码不一致(spec 写的 vs 代码写的差异)
- 哪些功能是按某种版本约定的(比如 v2.4 后才有)
```

### 段 6:收口语(2 行,固定格式)

```
摸完的程度: {读了哪些 / 没读哪些 / 颗粒度到"再听你一句话能立刻定位到文件模块"}
{用户接着说新需求就行}——比如 "你接着说新需求就行, 我已经掌握到 X 的颗粒度"
```

---

## 实际填写原则

- **数字优先**:"有 7 类意图" > "有多类意图"
- **路径必填**:每提到模块/服务就贴路径
- **代码块用 schema 不用文件**:协议段是字段表,不是贴 JSON 实例
- **不要重复段**:同一个事实只出现一次
- **段 4 用 bullet**:模块太多,平铺太占地方

## 反模式(不要这样做)

- ❌ 写"项目背景 → 技术选型 → 团队组成"——这是 Phase 0,不是立项书
- ❌ 把每个文件贴一段代码——你不是 CC,不要 copy 代码
- ❌ 用"按文件分节"组织报告——用户要的是架构视图
- ❌ 写"以下是详细分析:1. 模块 A 2. 模块 B 3. ..."——直接写要点
- ❌ 在段 6 问"你接下来想做什么"——用户下一步是他自己说,你等他就行

## 报告长度参考

典型规模:
- 段 1: 3-5 行
- 段 2: 30-80 行(含 schema 块)
- 段 3: 50-120 行
- 段 4: 50-100 行
- 段 5: 0-30 行(可选)
- 段 6: 2-3 行

**总计 150-350 行纯文本**(不算用户能看到的标题装饰)

超过 400 行 → 你写得太多了,该砍。

## 完成后

不要主动问"你需要我深入了解哪个模块"——这是 Phase 0 收口。用户下一步会自己说需求。如果他没说,他会说"再看看 X"或"差不多了",你再补一轮。
