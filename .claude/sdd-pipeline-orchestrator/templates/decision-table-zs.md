# zs-dev-orchestrator 决策表(跨项目通用)

> Layer 2 stage 编排 Agent 决策的"硬规则"。
> Layer 2 不重新发明规则——遇到情况,查本表。

---

## 1. 失败处理决策

| 场景 | 决策 | 升级到用户 |
|---|---|---|
| 同一 stage 失败 1 次 | 派 CC rewind(带具体原因),重试 | - |
| 同一 stage 失败 2 次 | 派 CC rewind(详细原因),重试 | - |
| 同一 stage 失败 3 次 | 暂停,生成失败报告 | ✅ 升级用户(附 3 次失败原因 + 尝试过的方案) |
| 同一 stage 失败 4+ 次 | 不再尝试 | (用户决策后) |

**rewind 触发条件**(CC 报告里发现这些,自动 rewind):
- CC 修改了不归本模块的文件
- CC 引入新依赖没说明理由
- CC 跳过测试
- CC 把"未完成"标"已完成"
- CC 写了"未授权"的代码(违反 hard_constraints_doc)
- CC 没回写 TASK 状态就开始下一 stage
- CC 返回的 verification 报告与实际不符

---

## 2. 架构偏离决策

| 偏离类型 | 严重度 | 决策 |
|---|---|---|
| 违反 hard_constraints_doc(明确规则) | Critical | rewind + 列出违反条款 + CC 修复 |
| 违反业务对象目录约定(文件放错位置) | Major | rewind + 提示正确路径 |
| 引入新依赖(普通库) | Major | rewind + 要求 CC 在 summary 说明理由 |
| 引入系统级依赖(数据库 / 消息队列 / 缓存类型变化) | Critical | 暂停 + 升级用户 |
| 改动跨模块公共组件 | Critical | rewind + 跑回归测试 |
| 改动项目入口文件 | Critical | rewind + 列出影响 + 升级用户 |
| 违反 spec 系统的命名规范 | Warning | 自动修复(在 verify 报告里警告) |
| 规则本身模糊(我不确定算不算偏离) | - | ✅ 升级用户(附具体规则原文 + 我判断) |

---

## 3. 业务需求决策

| 场景 | 决策 | 升级 |
|---|---|---|
| 业务需求歧义(Layer 1 阶段) | 生成 clarifications_needed,推用户 | ✅ 升级用户(任务开始前) |
| 业务需求歧义(Layer 2 阶段) | 派 CC 给 2-3 个方案,让 CC 收敛 1 个 | - |
| CC 收敛 1 轮成功 | 继续 | - |
| CC 收敛 2 轮成功 | 继续 | - |
| CC 收敛 3 轮仍不一致 | 暂停 | ✅ 升级用户(附 3 轮方案 + 各自优劣) |
| 同一模块 2 次回退到 brain | 暂停 | ✅ 升级用户(说明需求边界本身有问题) |

---

## 4. 推送降级决策

| 场景 | 决策 |
|---|---|
| `send_message` 成功 | 推飞书 |
| `send_message` 失败(SDK 缺 / 网络问题 / chat_id 错) | 降级到 `.meta-dev/notifications.log` |
| 飞书 SDK 完全不可用 | 改用本地日志,任务继续 |
| 用户长时间没回应(> 24h) | 不升级(用户可能没空),下次 session 继续 |

## 5. 用户介入决策

**找你的 6 种场景**(我会主动打断):

1. **同一 stage 连续失败 3 次** — 附 3 次失败原因、尝试过的方案、我的建议
2. **同一模块 2 次回退到 brain** — 说明需求边界本身有问题
3. **架构偏离规则本身模糊** — 附规则原文 + 我判断 + 我的猜测
4. **业务需求 3 轮收敛不了** — 附 3 轮方案 + 各自优劣
5. **引入系统级依赖** — 附建议(用什么 / 为什么)
6. **模块 done 后等你最终验收** — 附产物清单 + 验证证据

**不找你**的(我自己拍):
- 同一 stage 1-2 次失败,自动 rewind
- 同一模块 1 次回退,自动重试
- 架构偏离(规则明确),自动打回
- 引入普通依赖,警告 + 要求说明
- 业务需求 1-2 轮收敛
- 推送失败,降级到日志
- 验证证据完整,自动更新状态

## 6. stage 重路由决策

| 触发 | 重路由 |
|---|---|
| verify 不可开工 | 派 CC 修订 spec → 重 verify(最多 3 次) |
| verify 3 次仍不可 | 升级用户 |
| code-review 失败 | 派 CC 修复 → 重 code-review(最多 3 次) |
| e2e-run 失败 | 派 CC 修复 → 重 e2e-run(最多 3 次) |
| done 拒绝更新(有未收口项) | 派 CC 按责任阶段打回 → 重 done |

**不重路由**的场景:
- 用户已经验收的产物(避免误丢)
- 已经在跑的 stage(等当前 stage 跑完再决定)

---

## 7. 跨任务决策

| 场景 | 决策 |
|---|---|
| 队列里多个任务 | 跑完一个,自动开下一个 |
| 当前任务跑失败(未到升级用户) | 暂停,不让下一任务开始 |
| 当前任务需用户介入 | 暂停,等用户回复 |
| 用户新加任务 | 加到队列末尾(不打断当前任务) |
| 用户取消任务 | state.yaml 标 cancelled,不开下一任务 |

---

## 决策执行流程(Layer 2 操作)

```
1. 收到 CC 返回的 JSON
2. 检查 status 字段:
   - "done" → 走 stage-definitions.md 的验收标准,通过则写 state.yaml + 推消息
   - "blocked" → 走失败处理决策(看 attempts)
   - "needs_user" → 升级用户(附 CC 报告里的 issues 字段)
3. 跑 stage-definitions.md 的验收标准:
   - 通过 → 推消息
   - 不通过 → rewind 或升级
4. 写 state.yaml(更新 stage 状态 + stages 列表)
5. 推飞书(降级到日志)
6. 决定是否进下一 stage
```

## 诚实声明

- 这些规则是**默认**——你可以在 route-plan.yaml.parameters.hard_constraints 里加自己的规则覆盖
- 决策不是机械的——遇到边界情况,Layer 2(也就是我)会基于上下文判断
- 升级不是放弃——升级是为了让你做只有你能做的判断(业务、优先级、边界)
- 我可能错——如果你觉得我"过度升级"或"过度自动化",告诉我,我调整
