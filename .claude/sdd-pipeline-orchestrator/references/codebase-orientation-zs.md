# Phase 0: 代码库定向技术细节

适用场景:用户说"我有个新需求,先帮我理解我的代码"。你要在一次会话内把项目的当前实现梳理成结构化地图。

## 核心约束

**预算**:典型项目体量
- 后端核心代码 10-30K 行
- spec 文档 5-15K 行(REQ + DES + TASK + CHK)
- 前端核心代码 5-15K 行

**目标产出**:一份 200-400 行的"现状地图",足以让用户基于它描述新需求。

**这意味着你最多能读 30% 的文件,且要选对那 30%**。

## 第一步:定位边界(1-3 个工具调用)

```bash
# 1. 项目根扫一眼
ls <项目根>

# 2. 关键文档和目录
cat CLAUDE.md 2>/dev/null | head -50
cat AGENTS.md 2>/dev/null | head -50

# 3. spec 目录结构
ls specs/requirement/  # 列模块名
ls specs/design/        # 列模块名

# 4. 后端入口
cat <后端>/urls.py | head -30

# 5. 前端路由
cat <前端>/src/routes.tsx | head -50

# 6. 体量预算 —— 这一步最关键
wc -l <关键后端文件>...    # 一次列 10-20 个
wc -l <关键前端文件>...    # 一次列 5-10 个
wc -l specs/**/*.md       # spec 体量
```

**目的**:知道项目大概多大,知道哪些文件值得深入读。

**踩坑**:
- ❌ 跳过 `wc -l` 直接开读 → 后面 2000 行文件就 context 爆炸
- ❌ 只读 CLAUDE.md 就开干 → CLAUDE.md 通常只描述愿景,不描述现状
- ✅ 扫完一遍就形成"哪些文件是骨架、哪些是边角"的判断

## 第二步:选 spec 章节(3-5 个工具调用)

**不要全读 DES 正文!** DES 通常 1000-5000 行,读了 context 必爆。

正确做法:
```bash
# 1. REQ 总章读全文 —— REQ 通常短(<500 行),且含版本历史能告诉你"什么功能已实现"
# 2. DES 只读章节标题 —— grep 三级标题,判断结构
grep -n "^#{1,3}" <DES 文件>.md
# 3. CHK 读检查项汇总表(通常在前 100 行) —— 告诉你哪些功能"应验收通过"
head -100 <CHK 文件>.md
```

**目的**:
- REQ 告诉你"项目声称要做什么"
- DES 标题列表告诉你"实现分几层、几个关键模块"
- CHK 检查项告诉你"验收标准是什么"

**踩坑**:
- ❌ REQ 一份份读完 → 用户的需求可能只覆盖 1 个 REQ,你读了 10 个就为他人做嫁衣
- ❌ DES 全文通读 → 必爆,必超时
- ✅ 只读 REQ 主体 REQ + DES 章节标题 + CHK 验收项汇总

## 第三步:选代码骨架(4-8 个工具调用)

**找入口的思路**:
1. WebSocket / HTTP 入口:`urls.py` 里 grep 关键路由(比如 `searchask`、`rag_chat`)
2. 顺着路由找 `consumers.py` / `views.py`
3. 入口函数调到哪里(grep `def rag_chat_post` / `def xxx_post`)
4. 主链路函数调哪个 LangGraph / orchestrator
5. orchestrator 调哪些 service / node

**选择读哪些文件**:
- 入口文件(全文读,通常 500-1500 行)
- 主链路第一站(全文读,通常 500-1500 行)
- 主链路核心节点(选读 3-5 个,每个 200-800 行)
- 配置 / 协议定义(读关键段,grep 不全文)

**绝不读**:
- `__pycache__/`、`node_modules/`、`dist/`、`build/`
- 单文件 > 2000 行的(用 `grep -n` 定位关键函数段,不全文读)
- 单元测试文件(除非用户专门问)
- 老的 `.bak` / `.tar` 备份

**踩坑**:
- ❌ 一上来就 `cat` 主文件全文 → context 必爆
- ❌ 顺着目录树"按文件读" → 读了一堆边角,主链路反而没看清
- ✅ 先找入口 → 顺主链路读 4-5 个关键文件

## 第四步:交叉验证(spec vs 代码)

**目的**:发现"spec 写了但代码没实现"或"代码做了但 spec 没写"的偏差。

具体做法:
1. 读代码时,顺手 grep spec 里提到的关键名词(类名 / 函数名 / 协议字段)
2. 读 spec 时,grep 代码里的实际类名 / 协议字段
3. 标出 3 类偏差:
   - **spec 没写**:代码实现了 X 但 spec 没提(可能新需求已加,spec 没同步)
   - **代码没实现**:spec 写了 X 但代码没做(可能 TODO 或历史遗留)
   - **实现与 spec 不一致**:两边都写了但细节不同(注意哪个更新)

**意义**:
- 用户的"新需求"经常基于他对 spec 的理解
- 如果你发现 spec/代码不一致,直接告诉他,他能立刻纠正理解偏差
- 比"我读完了,你看需求"高效 10 倍

**踩坑**:
- ❌ 把 spec 当事实全信 → 给用户报告时把 spec 的"目标态"当"现状"
- ❌ 把代码当事实全信 → 错过"代码刚改但 spec 没更新"的版本号变化
- ✅ 报告里**两边都说**,并标出"已交叉验证"

## 第五步:输出地图(写一份结构化报告)

**报告必备 4 段**(每段 50-100 行):

### 1. 整体定位
- 一句话项目定义
- 技术栈 1 行
- 入口路径 1 行
- 协议形式 1 行(WS / HTTP / RPC / etc.)

### 2. 核心协议契约(必须用代码块)
- 消息 schema(JSON 字段表)
- 状态码 / 错误码
- 端点列表

### 3. 主链路(数据流图风格文字描述)
- 入口 → 校验 → 主处理 → 输出,每步哪个文件哪个函数
- 关键的分叉点(比如"如果是 A 则走 X,如果是 B 则走 Y")

### 4. 关键模块清单
- 列 5-10 个核心文件路径 + 一句话职责
- 列关键 Redis key / DB table / 外部 API
- 列"用户最可能想改的扩展点"(比如画像层、推荐服务、协议字段)

**可选第 5 段:踩坑信号 / 版本说明**
- 哪些 spec 章节"已知未实现"
- 哪些代码文件"看起来是新加的(spec 还没写)"
- 哪些地方用户没明确说过怎么处理

## 输出格式原则

- **不堆砌代码片段**——只在协议契约段贴 schema
- **不写"我觉得"**——只写"代码是 X / spec 写的是 Y"
- **不写"待确认"**——你读到啥就写啥,不确定的标"spec 没写 + 代码没显式做"
- **不要表格化一切**——文字段落 + 代码块更可读
- **报告结尾说"你接着说新需求就行"**——明确这是 Phase 0 收口

## 一次会话时间预算

| 步骤 | 工具调用 | 耗时 |
|---|---|---|
| 定位边界 | 5-8 | 1-2 分钟 |
| 选 spec 章节 | 3-5 | 1-2 分钟 |
| 选代码骨架 | 4-8 | 3-5 分钟 |
| 交叉验证 | 隐含在读文件里 | 同步发生 |
| 输出地图 | 1 次大 write | 1-2 分钟 |
| **总计** | **15-25 个工具调用** | **6-10 分钟** |

## 反模式(明确的错误做法)

- ❌ 一次会话只读一个 5000 行文件 → 用户等 20 分钟拿到 50% 信息
- ❌ 用 `delegate_task` 派 CC 做 Phase 0 → CC 看不到主对话上下文,产出与用户预期错位
- ❌ 用 `execute_code` 写脚本"自动化遍历代码" → 没必要,且容易把简单事做复杂
- ❌ 输出"按文件分章节"的报告 → 用户要的是"架构视图"不是"目录视图"
- ❌ 在报告里写"如果有问题请告诉我" → 这是 Phase 0 收口,用户下一步会说需求,你等就行
- ❌ 跳过 wc -l → 你会反复超时,反复重新规划读法

## 何时 Phase 0 应该升级成"派 CC 做完整调研"

罕见但有的场景:
- 项目代码量 > 100K 行(超出 Hermes 主对话 30 分钟预算)
- 用户需要的是"详细到函数级的全量文档"(比如要交给外部团队)
- Phase 0 读完后用户说"你说的不全,XX 模块呢"

此时:
1. 承认 Phase 0 已到预算边界
2. 派 CC 跑一个"调研 agent"——用 delegate_task,目标:产出全量架构文档
3. CC 完成后回到主对话,你基于 CC 的报告继续 Phase 0 → 接收新需求

不要假装一次会话能覆盖 100K 行代码。这不是 Phase 0 的目标。
