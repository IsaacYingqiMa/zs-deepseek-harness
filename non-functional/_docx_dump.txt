[0003] 状态：探索阶段，进入立项讨论

[0096] 4 我们的方案：基于zsspec构建自主编程OS
[0097] 4.1 核心判断：自主路线的5个取舍
[0098] 我对自主编程路线的看法是 —— 我们的方案不是什么都做，而是有清晰的取舍。下面几个取舍是后续所有架构与里程碑决策的源头。
[0099] 不做的 4 件事：
[0100] - 不自研Agent Runtime —— 优先复用现有/开源方案（候选：增强版 Hermes、DSH）。自研Runtime是6-12个月工程，与复用方案不可同日而语；但不预先锁定任何单一平台。
[0101] - 不绑定单一Coding Agent —— Worker层抽象为WorkerInterface，可挂Claude Code / Codex /国产模型。模型成本与能力波动剧烈，单一绑定是商业风险。
[0102] - 不一上来做多项目并行 —— M1只跑单项目POC。多项目并行是M2的工作，跨session续跑没验证就上并行是赌博。
[0103] - 不替换现有PR review / merge流程 —— 只在review前本地自动执行Code Review。现有流程承载团队信任，不能突然换轨。
[0105] 做的 4 件事
[0106] - 第一件：verify阶段自动化 —— ROI 最高、风险最低的切入点。当前 verify 是 LLM 自评 + 人工核查，对应痛点 P2、P9，是吞噬工程师时间最严重的地方。
[0107] - 第二件：apply阶段spec强制读取 —— 解决失焦（头号痛点 P1）。把相关 spec 强制到 apply 阶段内强制回读。
[0108] - 第三件：新增集成smoke test TDD —— Devin / Cognition 复盘公认的分水岭。
[0109] - 第四件：多goal并行+远程介入 —— 规模化的必经之路（对应 P4 / P5 / P6），但必须等前三步验证完才投入。
[0110] 我认为这个路线最优因为：
[0111] - 前三步都能在zsspec现有9个阶段内增量改造，不需要重写流水线。
[0112] - 每一步都可以独立开发 —— 做坏了不会污染其他步骤。
[0113] - 如果跑不通，意味着我们对”生成/验证分离”的判断错，应回退到现有 zsspec 优化
[0114] 贯穿全局的架构第一性原理：生成与验证必须分离
[0115] 自主编程的瓶颈不是生成代码，而是可信地验证代码。当前所有Agentic编程工具的共同反模式是：同一个Agent既写代码又自我判断——这必然导致记忆奖励、自我认可，以及必须有人盯着。
[0116] 因此本方案的第一性原理是：
[0117] 在架构上把生成者（Writer）与验证者（Verifier）彻底分离，并用可执行spec task和验证清单作为客观进入下一步的门禁。
[0118] 这条原理直接决定三件事：
[0119] - Verifier 必须是独立的对抗角色，不能和Writer共用上下文——否则它会看到Writer的自我辩解，失去对抗性。
[0120] - 验证以LLM/agent为主导，但必须有命令给出客观证据——LLM负责理解/翻译/解读/裁决，命令负责提供不可辩驳的exit code/反例/覆盖率。
[0121] - 语义模糊处用三路决策升级人（修代码/修规格/修测试），把人的精力从持续盯守压缩成在规格不清晰时才做决策。
[0123] 我认为：想清楚这一条，其他所有设计都是从它推导出来的。9个痛点追到根上是同一个问题——没有一套“不依赖人眼、也不依赖生成者自评”的可信验证机制。

[0140] 4.3 目标能力跃迁：从L3到L4
[0142] 我认为：L3 → L4的鸿沟本质是谁来验证。当前是LLM自评 + 人工核查，目标是独立 Verifier（LLM 主导）+ 命令客观证据 + 人只审 critical。这是自主与自动化的根本区别——自动化是脚本跑，自主是选择可信验证 + 异常分支自动选择处理通道 + 人只做兜底决策。

[0161] 4.5 核心架构：生成/验证分离的自主编程 OS
[0162] 4.1中给出了第一性原理（生成与验证分离），本节把它落成具体架构。分四部分：角色班子 → 验证阶梯 → 验证循环 → 平台栈。
[0164] 4.5.1 智能体角色班子（不是一个全能 agent，是一组互相制衡的角色）
[0166] 自主编程不该是一个全能 agent 单打独斗，而是一组职责单一、互相制衡的角色：
[0167] 两个关键点：
[0168] - 可执行规格翻译把验收清单从人看的文字变成机器能跑的证据——这是规格的可执行化。
[0169] - verifier是与 Writer 物理隔离的对抗角色。它的激励是”找出问题”而非”通过审查”，且看不到 Writer 的自我辩解，只看规格 + 代码 + 客观证据。这就是防记忆奖励的架构保证——不靠 prompt 求 agent”别骗自己”，而靠架构让它”没法自己骗自己”。
[0170] 编排层要”笨”，不要智能：Orchestrator 是确定性状态机，只做派发、重试计数、升级触发、检查点，绝不做”这个产出够不够好”的语义判断。如果把语义判断放进编排层，等于把”人盯”问题挪到编排层，信任问题没解决。
[0172] 4.5.2 验证层：4 级验证阶梯
[0173] 验证按便宜→贵分 4 级，多数错误在低级别几秒内就被拦截，走不到昂贵的 e2e——这直接缩短反馈周期：
[0175] 对验证该由谁主导的明确回答：
[0176] 验证必须以 LLM/agent 为主体，不能退化成纯 lint/规则。但要把主观判断与客观证据分开——LLM 负责理解、翻译、解读、裁决（语义层）；命令负责提供不可辩驳的客观证据：exit code、反例、覆盖率（事实层）。LLM 说我觉得对了不算数，必须有命令证据；但命令跑什么、结果怎么解读、失败怎么处理，由 LLM 主导。
[0178] Tier 2 的关键机制——可执行规格 + 属性测试：
[0179] CHK 验收项
排序后输出应与输入等长且单调不降
        ↓ Property Translator（LLM）翻译
可执行 Property：
   ∀ lst: len(sort(lst)) == len(lst) 且 is_monotonic(sort(lst))
        ↓ 属性测试框架（Hypothesis / fast-check）
   自动生成几百个随机输入执行
        ↓ 若失败
   反例 → shrinking 压缩成最小反例
        ↓
   最小反例喂给 Debugger 定位根因
[0181] 为什么这比单元测试强、又比纯 LLM 自评可靠：
[0182] 比单元测试强：单元测试是”例子”，只测你想到的；property 是”规律”，用随机生成覆盖你想不到的边界。
[0183] 比纯 LLM 自评可靠：property 的执行是客观的、不可被 LLM 花言巧语绕过；反例是具体、可复现的。
[0184] 对 LLM 友好：shrinking 给出最小反例，让 Debugger 精准定位，而不是在巨大失败输入里抓瞎。
[0185] 诚实声明（PBT 适用边界）：property 测试最适合纯逻辑 / 数据结构 / 契约类代码（如示例的排序）。对 UI、API 编排、带副作用的集成代码，往往难以写出有意义的 property，这类主要靠 Tier 3 行为验证（smoke / e2e）兜底。我们不指望 PBT 覆盖一切——它是验证阶梯中的一级，不是全部。
[0186] 4.5.3 单阶段验证循环（编排的具体形态）
[0187] 对每个阶段：
  1. 派发 Writer（注入规格上下文 + 强制引用规格段落）
  2. Writer 产出 + 声称完成
  3. 按"便宜→贵"顺序跑验证阶梯：
     Tier1 静态 → 通过才进
     Tier2 property → 通过才进
     Tier3 行为/集成
  4. 三级都过 → 派发独立 Verifier 做 Tier4 对抗审查
  5. Verifier 返回 PASS / FAIL（带具体问题 + 对应 spec 引用 + 证据）
  6. FAIL → 把问题喂回 Writer 重做（有界重试，≤3 次）
  7. 重试用尽 或 问题语义模糊 → 触发"三路决策"升级人
  8. 更新状态机 + 检查点（断点续跑）
[0188] 4.5.4 三路决策（人类介入的唯一常规形态）
[0189] 当验证失败且语义模糊时，Verifier 不硬判，而是把问题分类后路由给人，让人做几秒钟的三选一，而非半小时的逐行审查：
[0190] 这是”减少人的精力”的核心机制：人的角色从”监工”变成”裁判”——每次介入是几秒的选择题，不是持续盯守。这正是痛点 P8 的解药。

│   - Telemetry: OTel 后端 + webhook                            │
└─────────────────────────────────────────────────────────────┘
[0195] 我认为：这套架构的价值不在”又画了个分层图”，而在于它把 §4.1 的第一性原理落到了可执行的角色与流程上——生成与验证分离、编排保持确定性、人只做选择题。平台栈（L1-L5）只是运载工具，真正决定成败的是 L3 验证层的设计。
[0197] 4.5A Verifier 的实现形态：skill vs subagent vs 独立进程
[0198] 这是落地时绕不开的工程决策：对抗式 Verifier 到底用什么形态实现？ 下面给出对比与明确推荐。
[0199] 四种实现形态对比
[0200] 明确推荐
[0201] Property Translator → 用 skill。它是相对确定性的”规格→property”翻译，复用现有 zsspec-verify 改造即可，不需要隔离，成本最低。
[0202] Verifier（对抗审查）→ 必须用独立 subagent。这是整套方案的信任基石，绝不能用 skill（理由见下）。
[0203] Debugger → 用 subagent。需要”新鲜视角”看最小反例，不被 Writer 的思路带偏。
[0204] 为什么 Verifier 必须是 subagent 而非 skill
[0205] Verifier subagent 的输入/输出契约（关键设计）
[0206] 只注入这些（保证对抗性）：
[0207] 规格（REQ / DES / CHK）
[0208] 代码 diff / 相关文件
[0209] 验证命令的客观输出（exit code、反例、覆盖率）
[0210] 明确不注入（防污染）：
[0211] Writer 的自述、推理过程、“我觉得我做好了”之类的话
[0212] 输出结构化（供编排层判定）：
[0213] {
  "verdict": "PASS" | "FAIL" | "AMBIGUOUS",
  "issues": [
    { "spec_ref": "CHK-003", "problem": "...", "evidence": "..." }
  ],
  "route": "fix_code" | "fix_spec" | "fix_test" | null   // AMBIGUOUS 时给三路建议
}
[0214] 我认为：这个”输入白名单 + 输出结构化”的契约，是把”对抗式审查”从口号变成工程的关键。Verifier 看不到 Writer 的辩解、只对着规格和客观证据挑毛病——这才是”分离”二字的真正落地。
[0216] 4.6 差异化优势（含可插拔策略）
[0217] 4.6.1 vs 商业产品
[0218] 我认为：我们和 Devin 最大的差异不是技术，是 codebase 知识的深度 —— DeepWiki 是 Cognition 外部构建的（先有 Devin 再造 DeepWiki），而我们是原生集成（zsspec + 内部 codebase 是同一批人在维护）。这是商业产品短期内追不上的护城河。
[0219] 4.6.2 可插拔策略（不锁定 Coding Agent）
[0220] 按 §4.1 的核心判断，不依赖特定 Coding Agent：
[0221] Worker 层抽象为 WorkerInterface，可挂 CC / Codex / SWE-agent / 国产模型
[0222] Verifier 由独立对抗 agent 主导，命令提供客观证据——评测权不交给”被评对象本身”（即 Writer），但验证的判断主体仍是 LLM，命令只是不可辩驳的证据（见 §4.5.2）
[0223] Orchestrator 层可任意替换 coordinator 实现
[0224] 模型成本 / 能力波动时可热切换
[0225] 我认为：这是平台化而非单一产品的设计哲学 —— 这也是为什么 DSH / OpenHands 这类 runtime 框架比 Devin 更适合做长期演进。绑定一个 Coding Agent 等于把自己的命运交给一个供应商的更新节奏。
[0226] 4.6.3 编排平台的选型（分阶段，不锁死）
[0227] 编排平台的本质需求只有 4 条，任何平台满足即合格：①持久化状态机（断点续跑，对应 P4）②确定性阶段流转 ③带沙箱的子进程执行 ④事件/通知系统（升级、远程介入）。
[0228] 我认为：最该先回答的问题不是”用哪个平台”，而是”分离式验证 + 可执行规格，能否让验证可信到不需要人盯”。这个假设在 Hermes 上就能验证——假设成立，平台选型是工程问题；假设不成立，换什么平台都白搭。先验证价值，再选载体。
[0230] 4.7 实施路径：痛点驱动的三阶段
[0231] 每个阶段都明确解决哪些痛点 —— 这是 §4.4 映射表的执行版。每个阶段都有”对应痛点”+“具体工作”+“可量化成功标准”三件套。
[0232] 时间安排：三阶段各 1 个月，顺序推进，总计 3 个月（与 §5.2 / §7.1 一致）。
[0233] 阶段 1（M1，第 1 个月）：砍掉 P1 / P2 / P3
[0234] 目标：在 1 个示范项目上跑通”phase 自动 verify” + 解决 apply 失焦 + 接入真集成 smoke。
[0235] 对应痛点：P1 / P2 / P3
[0236] 具体工作（围绕”生成/验证分离”落地，编排平台沿用 Hermes 不更换）：
[0237] 实现 Property Translator（skill 形态）：把 CHK 翻译为可执行 property，复用并改造现有 zsspec-verify（针对 P2 的规格可执行化）
[0238] 实现独立 Verifier subagent：对抗式 system prompt + “输入白名单/输出结构化”契约（见 §4.5A），替代”Writer 自评”（针对 P2）
[0239] 实现 Tier1 + Tier2 验证：静态命令（tsc/eslint）+ property 测试（Hypothesis/fast-check，含 shrinking）（针对 P2 / P9）
[0240] 实现三路决策路由：验证失败且语义模糊时，分类推送”修代码/修规格/修测试”（针对 P2 / P8）
[0241] 扩展 handoff pack：spec 强制 inline + phase 内强制回读 + 要求引用规格段落（针对 P1）
[0242] 新增 stage 10：真集成 smoke（起服务 + 真实请求 + 抓日志）（针对 P3）
[0243] 成功标准（可量化）：
[0244] 选定 1 个具体示范项目（建议从现有 4 个 zsspec 项目中选 1 个）
[0245] 该项目跑完 5 个完整 feature，全 phase 经”4 级验证阶梯 + 独立 Verifier”
[0246] property 测试抓到的 bug 数 ≥ 单元测试抓到的（验证可执行规格的价值）
[0247] 人工介入次数较现状下降 ≥ 50%（验证”分离 + 三路决策”省精力）
[0248] 每个 phase 转换 ≤ 15 分钟人工介入；一性成功率 ≥ 50%（M1 是基础线，后续提升）
[0249] M1 末提交一份”验证层适用性报告”——含 4 级阶梯命中率、三路决策分布、false positive / false negative 案例
[0250] 阶段 2（M2，第 2 个月）：解决 P4 / P5 / P6
[0251] 目标：规模化前的最后一公里。
[0252] 对应痛点：P4 / P5 / P6
[0253] 具体工作：
[0254] 引入可持久化 runtime（候选 DSH / 增强版 Hermes，按 §4.6.3 评估结果选型）：session log + goal state + checkpoint + resume（针对 P4）
[0255] 实现 Multi-goal Queue：跨项目并行（针对 P5）
[0256] 接入 OTel + 自告 webhook（针对 P6）
[0257] 实现远程 pause/resume/rewind 命令
[0258] 成功标准：
[0259] 单人管 5+ 并行 goal 不卡顿
[0260] session 崩溃后 30 秒内自动 resume
[0261] 手机端能 pause/resume/rewind
[0262] 一性成功率 ≥ 70%
[0263] 阶段 3（M3，第 3 个月）：评估 + P7 / P8 / P9 收尾
[0264] 目标：量化收益 + 决策是否规模化。
[0265] 对应痛点：P7 / P8 / P9
[0266] 具体工作：
[0267] 量化所有 KPI（见 §5.3）：phase 转换耗时、一性成功率、并行项目数
[0268] 推广到 5–10 个项目验证
[0269] 与商业产品（Devin）做能力对照（参见 §3.3 能力矩阵）
[0270] 决策是否全面铺开
[0271] 成功标准：
[0272] 一性成功率 ≥ 70%
[0273] 每个 phase 人工介入 ≤ 15 分钟
[0274] 并行项目数 ≥ 4 个/人
[0275] 每月节省人工 ≥ 400 小时（见 §5.3 ROI 测算）

[0282] 5.3 KPI 与收益测算
[0283] 每个 KPI 都对应 §4.4 映射表中的痛点 —— 不是凭空设的，是被痛点驱动的。
[0284] 按月累计 ROI（15 人团队估算）
[0285] 说明：M1-M2 是纯投入期（仅构建），M3 末开始部分产出，M4+ 进入稳态。回本周期比”1.2 个月”更现实。
[0286] M3 月节省按 1/3 算（边评估边产出，团队还在适应）
[0287] M4 起稳态产出 25 万/月，对应 §5.3 计算明细
[0288] 收益计算明细（统一口径）
[0289] 每个工程师每天在 phase 转换上花约 1.5 小时（P2 + P9 是主要消耗）
[0290] 压缩到 15 分钟 = 每天节省 1.25 小时/人
[0291] 15 人 × 1.25 小时 × 22 工作日 = 每月节省约 412 小时
[0292] 按综合工程师成本（资深 + 普通加权）约 600 元/小时
[0293] 每月节省约 25 万元（412 × 600 ≈ 25万）
[0294] 说明：本计算只算 phase 转换节省的工时，没有算 P3（调试 agent 代码）/ P7（需求拉扯）/ P9（评测）等其他痛点带来的额外收益。因此 25 万/月是保守估算——实际可能翻倍。
[0295] 回本周期
[0296] 累计投资：~30 万元（2 人 × 3 个月 + 工具费用）
[0297] 稳态月节省：~25 万元
[0298] 从 M1 起算 ~5 个月回本；从 M3 完成起算 ~2 个月回本
[0299] 之后规模化收益线性增长
[0300] 我认为：这个回本周期是保守估算。实际收益可能更高——因为： 1. 节省的可能不止 phase 转换时间（bug 漏出减少带来的质量杠杆） 2. 跨项目并行带来的杠杆（4-6 个并行项目 > 4 个人的 4 倍工作量） 3. 知识积累（workspace memory）带来长期复利

[0303] 6.1 技术风险
[0304] 每条风险的缓解措施已在 §4 方案中明确 —— 这里给出”风险→方案”的对应关系，避免老板觉得”风险是事后补丁”。
[0305] 诚实声明（成本换可信度）：本架构用多个独立 subagent（Property Translator / Verifier / Debugger）+ property 测试来换可信度，token 消耗高于现在的”单 agent 自评”。这是”用成本换信任”的有意取舍，不是疏忽。缓解：分级触发——低风险阶段只跑 Tier1/2，高风险/收口阶段才上全套；并设 per-phase budget cap（见上表）。省下来的是更贵的人工注意力，账仍划算（见 §5.3）。
